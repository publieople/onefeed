# OneFeed V1 产品规格（001-v1-core）

| 项 | 值 |
|---|---|
| 文档版本 | 0.1（草稿，等待 OD-1 ~ OD-4 决策） |
| 更新日期 | 2026-11-13 |
| 目标交付 | 2026-11-28 黑客松现场可演示，2026-11-29 决赛路演 |
| 团队 | 3 人（产品/路演 1、前端 1、后端 1） |

## 1. 问题

同一个人同时泡在三个内容平台上：B 站看长视频、抖音刷短视频、小红书看图文。
每个平台都有自己的推荐算法，它们**互不知道对方看到了什么**，用户每天要在三个 App 之间来回切，重复看到同一件事的不同版本，还经常漏掉自己真正关心的那一条。

## 2. 目标用户

- 主要：我们自己（在校学生 / 开发者，日均刷 3 个平台，每个 ≥20 分钟）
- 次要：任何「账号是自己的、但内容散落在多个 App」的人

## 3. 核心场景

**SC-1 早八通勤**：打开一个页面，十分钟看完三个平台今天值得看的 20 条，不用切 App。
**SC-2 同一件事的多个版本**：一条新闻在三个平台被七个人讲，OneFeed 合成一张主卡，展开能看到各平台的说法和评论差异。
**SC-3 找特定内容**：输入「只看 AI 相关的」或「上海」，列表实时收敛，不用记哪个平台搜过什么。

## 4. 范围

### 4.1 V1 做

- 多平台采集（B 站、抖音、小红书；可选掘金）
- 统一数据模型 + 本地缓存（SQLite）
- 瀑布流混排 + 平台色标 + 详情抽屉（含评论）
- 登录态管理页（三档状态可视化）
- 跨平台去重合并（合并卡）
- 可解释排序（「为什么推给你」）
- 一句话过滤（自然语言 → 过滤条件）
- DEMO 兜底模式（离线 fixtures）

### 4.2 V1 不做

- 任何写操作（点赞/评论/发布/私信）
- 多用户、账号体系、云端同步
- 移动端 App（响应式网页够用）
- 视频下载、离线观看
- 快手 / 微博 / 知乎关注流（写进 roadmap，见 `docs/PLATFORM_NOTES.md`）
- 推荐算法训练（用规则 + embedding，不训练模型）

## 5. 功能需求

每条需求都给验收标准（AC），验收方式统一为「在本地跑起来能复现」。

### FR-1 平台采集
系统能从一个平台拉取不少于 10 条信息流内容，并归一化为统一 `Item`。
- AC-1.1 四个平台（B 站 / 抖音 / 小红书 / 掘金）各自 `python pull_all.py <platform>` 能打印 ≥10 条，字段含标题、作者、封面 URL、互动数、跳转链接。
- AC-1.2 单平台失败不影响其它平台（逐个 try，失败只记日志）。
- AC-1.3 单平台单次拉取耗时 ≤30s（含抖音浏览器冷启动）。

### FR-2 统一数据模型与缓存
- AC-2.1 `Item` / `Comment` 字段见第 7 节，缺值允许为 0 或空串，不允许 `None` 导致前端崩。
- AC-2.2 拉到的数据落 SQLite（WAL），重启服务后无需重新拉取即可展示。
- AC-2.3 同一 `id` 重复入库只更新时间戳，不产生重复行。

### FR-3 混排信息流
- AC-3.1 首页单列瀑布流，卡片显示：封面、标题、作者、平台色标、互动数、时间。
- AC-3.2 排序不按绝对时间（各平台内容时间分布差异大），按 `plan.md` 中的新鲜度分位数规则。
- AC-3.3 空态 / 加载态 / 错误态三种状态都有设计，不出现白屏。

### FR-4 详情与评论
- AC-4.1 点卡片右侧抽屉打开，含封面大图、标题、作者、跳转按钮、评论区。
- AC-4.2 评论带平台色标；B 站支持楼中楼展开；抖音显示热评前 5 条。
- AC-4.3 单条评论抓取失败时抽屉其余部分正常显示。

### FR-5 登录态管理
- AC-5.1 页面顶部平台 chip 显示四态：可用（绿）/ 即将过期（黄）/ 失效（红）/ 未配置（灰）。
- AC-5.2 未登录平台可一键触发扫码，二维码在页面内展示，扫码后 chip 变绿。
- AC-5.3 凭证只存本机，不进日志、不进导出文件。

### FR-6 跨平台去重合并
同一事件在不同平台的条目合并为一张主卡。
- AC-6.1 标题相似（simhash 距离 ≤3）或 embedding 余弦 ≥0.82 的条目归为一簇。
- AC-6.2 簇内互动最高的一条为主卡，其余折叠为「另外 N 个平台也在讲」，可展开。
- AC-6.3 合并精度人工抽查 20 条，误合并 ≤2 条（现场可接受阈值）。

### FR-7 可解释排序
- AC-7.1 每张卡片可展开「为什么推给你」，显示 3 条以内的具体理由（如「你关注了该作者」「同类内容你看完了 4 条」「今天 3 个平台都在讨论」）。
- AC-7.2 理由必须来自真实信号，不许写死文案。

### FR-8 一句话过滤
- AC-8.1 输入自然语言（如「只看 AI 和上海的」）后 2 秒内列表收敛。
- AC-8.2 解析结果以 chip 形式展示（可手动删除某个条件）。
- AC-8.3 无法解析时提示「没听懂」，不做错误过滤。

### FR-9 Agent 推送
- AC-9.1 后台按固定间隔（默认 30 分钟）跑一轮：采集 → 归并 → 排序 → 生成推送摘要。
- AC-9.2 打开页面时若有新摘要，顶部显示「今天新增 N 条值得看」。
- AC-9.3 推送摘要由模型生成，包含条数与一句话主题，禁止编造未采集到的内容。

### FR-10 DEMO 兜底
- AC-10.1 `ONEFEED_DEMO=1` 时零网络启动，全部数据来自 `fixtures/`。
- AC-10.2 从真实数据切到 DEMO 不超过 30 秒，页面无需刷新。

## 6. 非功能需求

- NFR-1 冷启动到首屏可看 ≤5s（本地缓存命中时 ≤1s）。
- NFR-2 服务只监听 `127.0.0.1`，不对外开放端口。
- NFR-3 单平台采集失败率在 3 次连续尝试内自愈（重试 + 退避）。
- NFR-4 前端在 1366×768 投影分辨率下布局不破。
- NFR-5 无外部付费服务依赖（模型调用除外，需可切换为本地/兜底文案）。

## 7. 数据契约

### Item

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | str | 带平台前缀，如 `douyin:7698...`、`bili:BV1...` |
| `platform` | str | `bili` / `douyin` / `xhs` / `juejin` / `v2ex` / `zhihu` |
| `raw_id` | str | 平台原生 id，用于调详情/评论 |
| `title` | str | ≤200 字 |
| `author` / `author_id` | str | |
| `cover` | str | 可直接 `<img src>` 的 URL，缺失为空串 |
| `url` | str | 原文跳转 |
| `published_at` | int | 秒级 unix，未知填 0 |
| `duration` | int | 秒，未知填 0 |
| `like` / `comment` / `share` / `view` | int | 缺失填 0，**不做跨平台可比性假设** |
| `fetched_at` | int | 采集时间 |
| `extra` | dict | 平台私有字段（话题、节点、标签等） |

### Comment

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` / `platform` / `item_id` | str | `item_id` 对应 `Item.id` |
| `author` / `text` | str | 文本 ≤500 字 |
| `like` / `reply_count` / `created_at` | int | |
| `replies` | Comment[] | 二级回复（B 站楼中楼、抖音 reply_comment） |

## 8. 待定决策（阻塞开发）

### OD-1 平台组合

| 选项 | 组成 | 优点 | 风险 |
|---|---|---|---|
| A | B 站 + 抖音 + 小红书 | 三个都是「你的流」，故事最干净 | 小红书登录、抖音稳定性两个风险点 |
| B（建议） | A + 掘金 | 技术内容补位，成本 40 行，免登录 | 掘金是「推荐」不是「关注」，要讲清楚 |
| C | B + V2EX + 知乎日报 | chip 多、视觉丰富 | V2EX 需代理、知乎日报无互动数据 |

**待确认**：A / B / C。

### OD-2 排序新鲜度算法

| 选项 | 做法 | 效果 |
|---|---|---|
| A | 绝对时间排序 | 老内容沉底，抖音新内容霸屏 |
| B（建议） | 平台内分位数：`freshness = 1 - rank_within_platform / n` | 各平台最新一条权重相同 |

**待确认**：是否采用 B。

### OD-3 产品形态

| 选项 | 用户看到 | 工作量 |
|---|---|---|
| A（建议） | Agent 预先筛过的流 + 顶部「今天新增 N 条」 | 需要 FR-9 |
| B | 全量未读流，Agent 只做标注 | 更简单，但失去「帮你筛」的卖点 |

**待确认**：A / B。

### OD-4 合并卡的地位

- A：核心卖点，路演主演示环节（技术风险最高）
- B：演示时成功就讲、失败就跳过（建议）

**待确认**：A / B。

## 9. 术语

| 词 | 含义 |
|---|---|
| 流 | 一个平台按推荐/关注下发的有序内容列表 |
| 合并卡 | 跨平台同一事件的聚合卡片 |
| 兜底模式 | 不发网络请求、只读 fixtures 的演示模式 |
| 分位数新鲜度 | 内容在本平台内的相对新鲜程度 |
