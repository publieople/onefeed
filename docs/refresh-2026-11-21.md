# 刷新为什么不换内容，以及平台抓取冷却（2026-11-21）

## 一、现象

点顶栏的刷新按钮、等进度条走完，首页还是那几张卡；强制刷新浏览器（Ctrl+F5）也不变。
任务要求：修掉它，同时加一个「每个平台的调用频率上限」，别让某个平台被调得太快。

## 二、根因：两个不同的问题叠在一起

### 1. 服务是以 `--demo` 起的，每轮都在重放同一份样例

`onefeed/service.py` 的 demo 分支每轮从 `fixtures/<pid>.json` 读冻结样例，再 upsert 进库。
upsert 按 id 去重 —— 同样的 id 只会更新字段，不会变多；排序键又固定，所以**条数、顺序都不可能变**。
前端刷新链路（`POST /api/refresh` → 轮询 `/api/progress` → `reloadKey + 1` 触发 `useFeed` 重取）本身是好的，
它确实重新请求了 `/api/feed`，只是库里没新东西。

更糟的是 demo 模式对外**不承认自己在重放**：`/api/health` 有 `demo: true`，但界面一个字都没说，
用户点刷新看到「开始刷新」和进度条，自然会以为在抓新的。

### 2. 没有发布时间的条目永远排不到前面

`FRESH_KEY` 原来是：

```sql
COALESCE(NULLIF(i.published_at, 0), i.fetched_at - 86400)
```

意思是「没抓到发布时间就当作一天前」。很多平台的条目本来就没有 `published_at`（知乎热榜、部分 V2EX 帖子），
于是刚抓进来的条目排序值比昨天抓的还小，即使真抓了新内容，首屏也看不到。

现在改成：

```sql
COALESCE(NULLIF(i.published_at, 0), i.fetched_at)
```

没发布时间的按抓取时间排；有发布时间的仍按发布时间。注意这是「同一平台内部」的新旧，
跨平台混排由 `page()` 的 `mix` 负责（见 `store.py` 的 platform 交错分支）。

## 三、修法

### 1. 演示模式不再装成刷新成功

- `/api/health` 的 `demo` 继续保留，前端在顶栏下面挂一条 `role=status` 的说明：
  「离线演示模式：内容来自本地样例，刷新只会重放同一批。要抓实时内容，用不带 `--demo` 的方式启动。」
- 一轮跑完后，完成提示按结果分三种：
  - demo：`演示模式：内容来自本地样例，这一轮只是重放，不会有新内容`
  - 全部冷却：`平台都在冷却中，最早 N 秒后才能再抓` + 一个「仍要抓」按钮
  - 真抓到：`刷新完成：新增 N 条 · M 个平台失败 · K 个平台冷却中`
- 演示模式里缺某个平台的样例文件时，不再静默跳过，抛 `FixtureMissing` → 该平台记 `skipped` 并带说明
  （「演示模式没有 xiaohongshu.json 的样例（在线跑一次 --warmup 就能补上）」）。

### 2. 平台级抓取冷却

**数据**：`settings.platform_intervals`，`{平台 id: 秒}`，缺省走 `DEFAULT_INTERVALS`：

| 平台 | 默认间隔 |
| --- | --- |
| bilibili | 300s（5 分钟） |
| xiaohongshu | 600s（10 分钟） |
| douyin | 600s（10 分钟） |
| zhihu | 600s（10 分钟） |
| zhihu-hot | 180s（3 分钟） |
| juejin | 300s（5 分钟） |
| v2ex | 300s（5 分钟） |

上限 `MAX_INTERVAL = 86400`（一天）。`0` 表示不限制。

**计数依据**：`store.last_pull_at(plugin)` 取 `MAX(COALESCE(NULLIF(finished_at,0), started_at)) FROM runs WHERE plugin=?`。
**失败也算一次调用** —— 被风控拦了同样是在打平台接口。

**判定**：`RefreshRunner._cooldown(pid, now)` 返回还要等多少秒；>0 就跳过，该平台记
`status="skipped"`、`next_at`、`note="平台冷却中，还要等 N 秒"`。
全部平台都在冷却时**不建线程**：`running=False`、`finished_at=now`、
`error="都在平台冷却中，这一轮没有实际抓取"` —— 前端据此立刻给「仍要抓」。

**三种放行**：`force=True`（用户点「仍要抓」）、`warmup`（首次预热）、demo 模式。
演示重放不写 `demo=0` 的 run（`runs.demo` 列，schema 8），所以不消耗真实预算。

**为什么按平台而不是按整轮**：一轮里 7 个平台各有各的限速，把整轮卡住会让一个慢平台拖死其它平台；
按平台算，B 站刚抓过就只跳过 B 站，其它照抓。

### 3. 设置项

设置页「采集与排序」里新增「平台抓取间隔」：7 个数字输入，单位分钟，`min=0 max=1440`，
`aria-label="<平台> 抓取间隔（分钟）"`，写回时换算成秒。保存后的提示会明确说改了几个平台：
`已保存：平台间隔 → 3 个平台改过（下一次抓取生效）`。

顺带修了一个会让保存提示误报的老问题：`_apply_settings` 原来把「registry 被规范化」也算进 `applied`，
于是保存一个数字也会提示 `registry → https://cdn.jsdelivr.net/gh/…`。现在只有值真的变了才上报。

## 四、实测

服务切到真实模式（`python -m onefeed --no-browser --port 8799`，`ONEFEED_HOME=.onefeed`，
`/api/health` 的 `demo` 为 `false`）。

| 项 | 结果 |
| --- | --- |
| 第一轮真实抓取（约 110s） | bilibili ok 9、douyin ok 10、juejin ok 12、v2ex ok 10、zhihu ok 12、zhihu-hot ok 12；xiaohongshu failed（未登录，见下） |
| 条目数 | 961 → 1011 → 1067 → 1155 |
| 首屏 | 摘要行「库里共 N 条」，V2EX「健身卡降价求支招」、知乎「华尔街巨头开源 AI 神器」等新条目出现在最前面 |
| 立刻再点刷新 | 全部 `skipped`，每个平台带 `note="平台冷却中，还要等 N 秒"` |
| 全部冷却时点刷新 | 立刻提示「平台都在冷却中，最早 3457 秒后才能再抓」+「仍要抓」 |
| 点「仍要抓」 | 提示「开始抓取（已跳过平台冷却）」，运行态正常出现并跑完 |
| 设置页间隔 | 7 个输入框，改 v2ex → 6 分钟保存，`GET /api/settings` 的 `intervals.v2ex` 变 360；恢复 5 分钟后回到 300 |
| 演示模式横幅 | 切真实模式后不再出现 |

探针：`probes/probe_refresh_live.py`（横幅、摘要行、首屏卡片、刷新提示、设置输入，产出
`probes/out/refresh-live.json` + `refresh-cooldown.png` + `settings-intervals.png`）、
`probes/probe_refresh_paths.py`（两条刷新路径，产出 `probes/out/refresh-paths.json`）。

## 五、已知限制

- **小红书未登录**：真实抓取时返回 `RuntimeError: [xiaohongshu] 小红书未登录：请在客户端扫码登录`，
  65 秒后失败。需要在设置页「登录态」里扫码；在此之前该平台每轮都算一次失败调用（也会进冷却）。
- 冷却按进程内 runner + 库里的 runs 表算，重启后仍有效；但如果手动清了 `runs` 表，冷却就没了。
- 演示模式仍会在没有样例时跳过平台，只是现在会说出来，不再静默。

## 六、回滚

- 想回到旧排序：把 `onefeed/store.py` 的 `FRESH_KEY` 改回 `fetched_at - 86400`。
- 想关掉冷却：设置里把所有间隔设为 0，或把 `DEFAULT_INTERVALS` 置空。
- 想让演示模式也「变内容」：不可能 —— 样例是冻结的，正确做法是用不带 `--demo` 的方式启动。
