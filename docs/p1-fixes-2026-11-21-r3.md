# 第三轮评审的 P1/P2 修复（2026-11-21）

基线 `cec0def`，评审报告 `docs/interaction-perf-review-2026-11-21-r3.md`。
口径沿用报告：P1 = 高频操作卡顿或反馈缺失（用户能直接感觉到），P2 = 打磨，P3 = 小目标，无 P0。

这一轮修了三条 P1，外加报告里风险低、能一次扫掉的 P2/P3。

## 一、P1：收藏框不压热键栈（C-01 / I-02）

**病**：`FavoriteDialog` 只锁了滚动，没进 dialog 作用域。开着收藏框按 `[` 把左栏从 240 收到 64、按 `t` 换肤、按 `?` 在收藏框上再叠一层帮助（评审实测 dialog 数 1→2）。

**为什么只有它漏**：压栈是每个弹层自己 `pushScope("dialog")` 的散装写法，Lightbox 和 Confirm 写了，收藏框忘了 —— 靠人记就一定会漏。

**改法**：
- 新 `web/src/motion/useModalScope.ts`，一行接入所有 `role="dialog"`。现在 Confirm、ShortcutHelp、Lightbox、FavoriteDialog、CardMenu、AgentSheet 全部走它。
- `useHotkeys` 的作用域栈从「数组里塞条目」改成**计数**（`depth: Record<Scope, number>`）。旧写法两层弹窗只会留一个 dialog 条目，先关内层会把外层的作用域一起掀掉。
- 守门测试 `test_every_dialog_takes_over_the_hotkey_stack`：扫 `web/src/**/*.tsx`，凡出现 `role="dialog"` 的文件必须出现 `useModalScope`，再也没法忘。

**实测**（1440×900，收藏框开着逐键按）：

| 按键 | 期望 | 实测 |
| --- | --- | --- |
| `[` | 左栏宽度不变 | 240 → 240 |
| `t` | 主题不变 | light → light |
| `?` | 仍只有 1 层 dialog | 1 |

## 二、P1：详情页拆包（C-03）

**病**：`FeedPage`、`ItemPage` 都是静态 import，519KB 一个包，首屏就把详情页、灯箱、收藏框、评论全下载了。Fast 3G + 4× CPU 下首卡 9.4s、LCP 9224ms、长任务 5634ms。

**改法**：
- 新 `web/src/pages/itemPageLoader.ts`：`loadItemPage()` 惰性 `import("./ItemPage")`，`itemPageLoaded()` 查是否已就位。`App.tsx` 用 `lazy(loadItemPageComponent)`。
- 三条预热路径：卡片指针进入/聚焦（和原有的数据预取同一条 600ms 去抖）、卡片 `pointerdown`、`openItem` 里兜底 `await`。
- **转场不被骨架打断**：`openItem` 先看模块到没到，没到就等它到再 `runNav`。如果直接 `navigate` 让 Suspense 接住，View Transition 拍到的就是那屏灰条。
- 原来的注释「详情页必须跟着主包一起到」已删除 —— 那个理由只在「模块没预热、转场拍到骨架」时成立，等模块即可。

**产物**：

| | 拆包前 | 拆包后 |
| --- | --- | --- |
| 主包 | 515.14 kB / gzip 165.96 kB | **451.54 kB / gzip 143.85 kB** |
| 详情页 | 含在主包 | 独立 `ItemPage-*.js` 63.55 kB / gzip 22.74 kB |

**实测**（`probes/probe_r3_fixes.py`）：
- 首屏资源里没有 `ItemPage-*.js`（0 个）。
- 指针进入卡片后请求该 chunk（1 个）。
- 点进详情 120ms 内 `[data-vt="media"]`、`[data-vt="title"]`、`h1` 全在，`main > .pt-10`（Suspense 骨架）为 0。

**限速冷启动**（Fast 3G + 4× CPU，6 次取样，`probes/probe_r3_throttle.py`）：

| | 评审基线 | 本轮中位 |
| --- | --- | --- |
| 首卡 | 9.4s | **6.6s**（6.0–7.3s） |
| LCP | 9224ms | **约 8.9s**（8.4–9.5s） |
| 长任务合计 | 5634ms | **2.7–3.9s** |
| 请求数 / 传输 | 33 / 912KB | 25–26 / 706KB |

**还没解决的**：LCP 元素是卡片封面 `IMG`，不是 JS。4× CPU 下渲染 18 张卡仍有 1.3–2.3s 的单段长任务，图片本身也没降采样（B 站 1890×1063 塞进 343×193 的框）。下一步该做的是采集层存缩略图 URL + 首屏前两张 `fetchpriority="high"`，那是采集侧改动，不在这轮。
主包 451KB 也没到报告建议的 <300KB：React + framer-motion + AgentProvider 还在主包里；再往下拆要把 AI 面板整条链路也惰性化，收益/风险比这轮不划算。

## 三、P1：Agent 心跳（I-01）

**病**：一轮 49.85s 的采样里最长 19.28s 可见文本一字未变，12s 截图只有一行静态「下一步…」+ 停止键。用户分不清"在跑"和"卡死"。

**为什么原来是死的**：`AgentConsole` 里其实有 `quietSeconds`，但它 6 秒内不变、且夹在「下一步…」那行小字里；更关键的是列表只在 `live.events.length` 变化时贴底，心跳变化不触发滚动 —— 所以看起来完全静止。

**改法**：
- 计时从「最后事件」改成**整轮开始**：`startRef` 在 running 变 true 时记 `Date.now()`，1s 一次刷新 `now`。
- 底部常显「还在跑 12s · 检索 [AI、大模型] · bilibili」：秒数每秒跳，阶段取最后一行事件的标题。秒数 `aria-hidden`，只让读屏念阶段，免得每秒播报。
- live 分支加两行 `animate-pulse` 缩略图占位 + 「结果在回来的路上…」，结果没回来时不再是一片空白。

**实测**（`probes/probe_r3_fixes.py`，每 600ms 采样 22s）：35 次采样里 35 次都有心跳文本，出现 **22 个不同取值**，第一秒就是 `还在跑 0s · 正在想`，之后按秒推进、阶段随之从「正在想」变成具体检索条件。评审说的 19s 静止在这个版本复现不了。
